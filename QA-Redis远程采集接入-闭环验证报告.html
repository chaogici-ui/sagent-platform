阻断级（不修就无法闭环）

B1探路步骤在 L0 进程内执行，而 L0 到被管网段没有路由

preflight_host 与 preflight_remote 都在 L0 进程内执行（前者走本机 ansible，后者走「执行包 + 人工回报」）。 但 L0 只挂在 l0-net，采集机与目标在 l1-net，两侧无路由——

后果：远程采集在这个环境下 100% 卡在探路，且 preflight_remote 会先傻等 3600s。 探路按设计就该在"真正执行采集的那一侧"跑（remote.yaml 注释里也这么写），即需要把探路搬到 L1 侧执行端——当前未实现。

B2采集目标被绑到"资源"而不是"采集机"，采集机永远拿不到这条目标　已修复

新建流水线的第一轮推进里，pick_proxy 选定采集机后只写了 flow.agent_id，没有同步回填内存里的 run.agentID； 而紧随其后的 collect_params 正是用 run.agentID 建目标，于是拿到的还是水合时的旧值 flow.ResourceID。

onboard_atoms.go:105-111   run.agentID = flow.AgentID；为空则回落 flow.ResourceID  ← 整轮只水合这一次
onboard_atoms.go:582 / 612 pickCollectorAgent: catDB.UpdateFlowAgent(...)  ← 只改库，没改 run.agentID
onboard_atoms.go:736       AgentID: r.agentID                             ← collect_params 用的是内存值

实测：首次 collect_params 落库的 agent_id = ip-10-20-0-15（资源 ID）， 不是 order.prod.mysql.proxy-02（采集机）。而 syncAgentConfig 是按 agent_id 取目标， 所以采集机那一版配置里根本不含这条 Redis 目标（当时配置停在 cfg-214，与接入前完全一致）。 人工删掉该行、重跑 collect_params 后 agent_id 才变成 order.prod.mysql.proxy-02，配置随之推进到 cfg-554 —— 反向印证了这是"同一轮内读到旧值"。

修复（2026-10-07）：库与内存一次写穿。新增 flowRun.bindAgent()，把「写库」和「回填 r.agentID」收敛成一个动作， pickCollectorAgent 的四处绑定（边缘模式 / 已选定 / 池内无健康采集机回落 / 自动挑机）全部改走它； collect_params 开头再以库为准兜一次底（GetFlow 读到非空 agent_id 就覆盖内存值）， 即便将来新增的原子能力在同一轮内改绑承载机，也不会再读到旧值。

onboard_atoms.go  func (r *flowRun) bindAgent(catDB, agentID) { r.agentID = agentID; catDB.UpdateFlowAgent(...) }
onboard_atoms.go  atomCollectParams 开头：if f := GetFlow(...); f.AgentID != "" { r.agentID = f.AgentID }  ← 兜底

回归测试：TestAdvanceFlowBindsTargetToCollectorInSingleRun —— 构造 flow.AgentID 为空的场景， 单次 advanceFlow 连跑 pick_proxy → collect_params，断言目标 AgentID 落在采集机、且 flow.agent_id 同步。

逻辑级（状态机与流程语义）

L1门禁失败后，不受依赖约束的步骤照常执行，业务对象被误标成平台设备

preflight_host 已 fail，但 register_platform_device 仍落 ok、self_metrics 落 running、 install_agent 落 skipped。原因是这三步的 requires 链不经过探路门禁， 所以"前置探路失败"对它们不构成阻断。

更实质的问题是 register_platform_device 无条件改写 r.resource 的角色：

onboard_atoms.go:771   catDB.UpdateResourceRole(r.resource.ID, "platform_device")

而远程模式下 r.resource 是被采对象（业务资源），不是采集机。实测资源 ip-10-20-0-15 的 role 已从 business 变成 platform_device —— 一个业务对象被登记成了采集平台自己的设备。

L2一步 blocked 让整条流水线对 Agent"关门"，running 步骤永久死锁

pick_version 因为等不到探路实测的 OS/架构而落 blocked， computeFlowStatus 于是把整条流水线判成 status=blocked； 而 Agent 自动回报的入口只认 status=running 的流水线：

onboard_api.go:780-795
  flows, _ := catDB.ListRunningFlows()
  ... if f == nil { "该 agent 无待回报的 running 流水线" }

实测采集机日志每 10 秒刷三条被拒记录，无限循环：

[INFO] [l0] 自动回报暂不被接受（self_metrics）：该 agent 无待回报的 running 流水线
[INFO] [l0] 自动回报暂不被接受（preflight_ability）：该 agent 无待回报的 running 流水线
[INFO] [l0] 自动回报暂不被接受（config_applied）：该 agent 无待回报的 running 流水线

后果：self_metrics / verify_probe / observe_collect 三个步骤停在 running， 既等不到回报、又不会超时判死（它们不在平台托管路径上，规格回落 default），形成静默死锁。

L3超时策略表里存在"死配置"：写了但永远不会生效

onboard_config.json 给 preflight_ability 配了 run_sec=300 / idle_sec=120 / retry=1， 但超时规格的选取逻辑是：平台托管或 Agent 域步骤才按 步骤ID/atom 取规格，其余一律回落 default。

onboard_timeout.go:475-483

  return timeoutSpecFor(cfg, "")     // ← default 3600s / retry 0

而 preflight_ability 既非平台托管、scope 也不是 agent，于是实测报出： 步骤超时（无响应 上限 3600s），已自动重试 0 次仍未完成 —— 配的 300s/重试1次一次都没用上。

L4sync_config 报 ok，但配置里可能没有本次接入的任何东西

第一次强制通过两道门禁后，sync_config 返回 期望配置已生成（cfg-214） —— 版本号与接入前完全相同，因为当时 Redis 目标被绑在错误的 agent 上，渲染出的配置体与旧版逐字一致。 步骤状态是 ok，但"这次接入"没有在配置里留下任何痕迹。步骤成功 ≠ 内容正确。

易用性与配置级

U1向导不提示"该采集能力数据面尚未实现"

采集模式、采集能力、采集参数三处都把 Redis 当作一等信息展示，插件目录里 Redis 的 params.yaml / dashboards / alerts 全都齐全，用户按界面提示一路走完， 最后只能在采集机日志里发现 本版不支持，已跳过。平台侧无任何前置提示。

U2探路失败的排查提示指向错误方向

界面给的是 目标机不可达或防火墙丢包；端口不对也可能表现为挂起超时。 但在远程采集场景下，更可能的真相是"L0 本来就没有到该网段的路由（探路应由采集机侧发起）"。 运维会照提示去查目标机防火墙，方向从一开始就错了。

U3「强制继续（需留痕）」的例外通道在无头/自动化环境不可用

接入流水线创建的 Redis 目标 tenant_id 为空，而历史 mysql 目标为 'default'。 多租户隔离（D3）全链路依赖该字段，空值会走 IFNULL 兜底，但落库口径不一致本身是隐患。 同一条目标的 region / candidates_json / preferred_owner 也全为空， 与采集机池化（漂移/回切）所需的字段不齐。

三、B3 修复：SAgent 数据面接入 redis-exporter

修复方向（按用户裁定）：SAgent 不主动监控任何组件，中间件指标一律由第三方 exporter 负责采集。 SAgent 只做三件事——把 exporter 二进制取到本地并校验、把 exporter 进程拉起来、把 exporter 暴露的 /metrics 按目标编排并抓入链路。Redis 指标因此由 redis-exporter 负责，SAgent 不解析 Redis 协议。

3.2 就近取包：SAgent 如何拿到 exporter

ensureBinary() 按三步解析——命中即用 → 不一致回源 L0 重建 → 重建后仍校验不过才拒绝。 缓存 sha 与权威不一致时不会直接拒绝，而是回源 L0 重新下载重建（这才是"就近取包"的本意： 省掉大文件下载，而不是拿缓存当终审）；只有回源下载后 sha256 校验仍不过才拒绝拉起，不降级用未校验二进制：

① 静态路径  plugins/redis_exporter/redis_exporter  → 命中即用
② 取权威清单 GET /api/plugin-packages/redis-exporter/manifest （L0 权威 sha256，小文件）
   本地缓存  data/packages/plugins/redis-exporter/<ver>/  → sha 与权威一致即用（省下载）
③ 回源 L0   GET /api/plugin-packages/redis-exporter/download （下载 → sha256 校验 → 落缓存）
           校验不过一律拒绝，不降级用未校验二进制
