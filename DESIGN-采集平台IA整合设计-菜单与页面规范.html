SAgent 采集平台 · IA 与页面设计规范（整合版）2026-09-26 · 融合来源：平台化设计原型（2026-09-22）语义层 + 7 条 IA 原则 + 真前端现状（9 页 4 组）· 目标态 12 页 5 组

设计观一句话：采集平台的菜单不是功能清单，是一条「接入 → 采集配置 → 运维观测」的闭环叙事；每个页面用一句话主问题验收，写不出主问题的页面就是设计有问题的页面。所有子功能以操作（谁在什么页面上做什么）定义，不做功能点堆砌。

01设计原则（菜单由这些推导）

#原则对本设计的约束
1每页只回答一个问题页头副标题 = 主问题，12 页各一句，见每张页面卡页头
2「总览」全站只出现一次工作台是唯一总览；「实时总览」改名「采集目标」并降为只读
3一个对象只有一个可写入口对象写操作只在接入中心；修复复核只在变更中心；其余位置只读+下钻
4数据同源，下钻代替复制对账引擎判决卡留在采集健康，数据治理页只放治理切片，互相下钻
5变更必留痕，审计只读变更中心 = 过程聚合；审计日志 = 合规原始记录；分工写进两页页头
6菜单两层封顶，全站 ≤12 页5 组 12 页，每组 2~3 项
7按闭环叙事分组分组 = 用户心里的追问顺序：现在怎么样 → 要接什么 → 拿什么采 → 数据如何 → 平台活着吗

02第一部分：菜单与子功能菜单

2.1 目标菜单树（5 组 · 12 页）

① 总览健康—— 现在怎么样？
工作台 已有主问题：现在最要紧的事是什么？ 结论卡（自动一句话）· 待办队列（未复核草案 / 待批准变更 / 受阻任务）· 健康证据链概要（下钻采集健康）
采集健康 已有·改造主问题：采得全不全、断在哪一环？ SLO 结论条 · 断采清单（四值状态）· 证据链归因（六环下钻）· 修复草案生成（只读预览→跳变更中心）
② 接入—— 要接什么、谁动了它？
接入中心 原「资源与接入」改名主问题：管哪些对象、归谁、接没接上？ 对象台账（唯一可写入口；本机 Agent 与远程对象同一本台账）· 接入向导（两条路径：本机装 Agent / 远程采集）· 卸载 / 启停发起（执行走变更中心）· 租户归属调整
采集目标 实时总览改名·降只读主问题：每台采什么、分派给谁？ 目标×插件×承载 只读矩阵（远程目标显示承载采集机与池）· 行下钻（跳接入中心修改）· 变更中/漂移标记（关联变更单号或漂移记录）
变更中心 从「系统」组移入主问题：谁动了它、怎么走过来的？ 变更流水线时间线（四段式）· 修复草案复核（全站唯一复核入口）· 预演 / 批准 / 执行 / 验收
③ 采集能力—— 拿什么采？
插件与策略 采集策略改名主问题：用什么采、怎么采？ 插件市场（安装走变更中心）· 采集策略（间隔/标签/路由，配置版本不可变）· 策略预演（三问卡片）
版本与兼容 从「系统」组移入主问题：用哪个版本、装不装得上？ 版本清单 · 兼容矩阵 · 自动选版规则（对应 PLAN-SAgent版本兼容矩阵，定义侧先行）
④ 数据观测—— 数据长什么样、干不干净？
指标大屏 分析大屏改名主问题：数据长什么样？ Grafana 嵌入（导航壳）· 指标浏览（只读跳转）
数据治理 新建主问题：数据干不干净？ 野指标对账清单（recon 切片，判决卡在采集健康）· 高基数治理（关闭 series / 丢弃率）· 治理建议（确认后走变更中心）
⑤ 平台—— 平台自己活着吗？
平台设置 已有主问题：平台怎么配？ 租户与 Token（D3）· 网络域与端点 · 集成（webhook 按 env 启用）——所有配置改动写审计
审计日志 已有主问题：谁在何时做了什么？ 只读原始留痕（合规记录，不聚合不加戏）
平台健康 新建·可先做设置内卡片主问题：平台自己活得好不好？ L0 组件逐项状态（console/PG/VM/vmalert/grafana）· L1 采集机池状态（L1HA 角色矩阵）· 对账引擎心跳（全自动，无人值守）

2.3 三条操作动线（菜单是按这个组织的，不是按技术模块）

动线 A · 接入模式 —— 一台新机器 / 一批远程对象从登记到出数
接入中心登记→ 接入向导本机装 Agent / 远程采集→ Agent 安装或远程插件下发 · 心跳自动上报→ 状态翻转 · 变更中心留痕→ 采集目标核对分派→ 工作台待办清零
人工只碰两个页面：接入中心（登记+向导）、采集目标（核对）。其余全自动。
动线 B · 采集配置模式 —— 改一次采集策略的全过程
插件与策略选插件定策略→ 策略预演三问卡片→ 变更中心批准→灰度执行→ 独立验收（recon）→ 采集健康看验收结论
预演先回答三个问题：影响哪些目标？成本区间多少？如何验收？——不回答不进变更中心。
动线 C · 运维模式 —— 从发现断采到闭环
采集健康发现异常→ 证据链定位断在哪一环→ 修复草案自动生成→ 变更中心人工复核→转变更→ 执行+验收→ 回写健康页
草案只是建议（模板输出不是 evidence），复核和转变更的动作只发生在变更中心——规则 3。

操作流程（远程采集接入，端到端）
  1. 人工接入中心「＋接入对象」→ 选「远程采集」路径 → 选插件（MySQL/Redis/Kafka/ES/ClickHouse/HTTP 拨测）。
  2. 人工两步分离：① 选采集机池（默认池内自动推荐一台承载最少者，可改选）；② 配被监控对象（多条批量，探活实时反馈）。
  3. 自动预检双闸：preflight_host（承载机就绪）+ preflight_remote（目标连通）——未通过不得进预演。
  4. 人工预演（影响目标数 + 采集频次 + 验收方式）→ 变更中心批准 → 执行：配置下发承载机 → 插件启动 → verify_probe → 观察采集窗口。
  5. 自动运行态：承载机失效 → 池内短心跳（10s）判故障 → 自动漂移到池内健康成员（单归属、先新后旧、预热接管秒级启动、端到端 ≤45s）→ 漂移记录留痕 + 工作台待办。
状态与样式要点
  1. 探活 chip 三态即时反馈：--teal-soft 连通（带延迟数）/ --red-soft 拒连 / --amber-soft 超时重试中。
  2. 漂移行：删除线旧承载 + amber 左边框 + 端到端耗时徽章；数据源与 HA-3 归属迁移记录卡同源（relocations 表）。
  3. 池健康 <2 保护态用 --error chip 置顶展示，明确「已停止漂移、仅告警」的语义（不静默）。
  4. 口令等敏感字段全程掩码，编辑时不回显明文。
